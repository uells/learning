## Термины
- **D7 (ядро D7)** - актуальное ядро CMS 1С-Битрикс, представленное в 2012 году. Оно пришло на смену устаревшему процедурному подходу и реализовано на базе современных стандартов PHP (пространства имён, ООП, ORM). Поскольку не все модули были переписаны под новое ядро, старое и новое ядро сосуществуют параллельно, и разработка может включать элементы обоих подходов.
- [**Table Model**](https://design-pattern.ru/patterns/table-module.html) - это шаблон проектирования, при котором вся логика работы с таблицей базы данных (чтение, обновление, удаление, выборки) инкапсулируется в одном классе.
- [**Domain model**](https://design-pattern.ru/patterns/domain-model.html) - шаблон проектирования, который строится вокруг бизнес-сущностей: каждый объект в коде представляет конкретный экземпляр из предметной области (например, один заказ, один пользователь). Логика размещается внутри этих объектов, они могут связываться друг с другом, поддерживать состояние и участвовать в моделировании бизнес-процессов.
- "**сущность**" (Entity) в контексте ORM и HL-блоков означает объектную модель какого-то набора данных, как правило, соответствующую конкретной таблице или логической сущности в базе. Проще говоря, сущность – это класс, описывающий структуру и свойства определённых данных, и позволяющий с ними работать как с объектами.
- **ORM(Object-Relational Mapping)** - это подход в программировании, при котором данные в базе данных отображаются на объекты в коде. Проще говоря, вместо того чтобы писать SQL-запросы (`SELECT`, `INSERT` и т.д.) вручную, разработчик работает с классами и объектами, а фреймворк сам «переводит» эти действия в SQL.




```php
// Без ORM
$result = $DB->Query("SELECT * FROM my_table WHERE ID = 1");
$row = $result->Fetch();
echo $row['NAME'];

// C ORM (Bitrix D7)
use MyNamespace\MyTable;
$row = MyTable::getByPrimary(1)->fetch();
echo $row['NAME'];
```

## Highload-блоки

### ORM в 1С-Битрикс
**ORM (Object-Relational Mapping)** — это способ работы с базой данных через объекты, а не через SQL-запросы или массивы. В 1С-Битрикс ORM появился в ядре **D7**. Он позволяет описывать таблицу как класс, а поля таблицы — как свойства объекта. Благодаря этому структура данных становится доступной для IDE, типы и связи описываются явно, и код становится более читаемым и безопасным.

#### Ключевые признаки ORM-подхода:

* Таблица описана как PHP-класс (наследник DataManager)
* Поля определены в `getMap()`
* Запросы делаются через `getList()`, `add()`, `update()`, `delete()`
* Можно описывать связи через `reference`
* Примеры классов: `ElementTable`, `UserTable`, `HighloadBlockTable`

#### Пример ORM

```php
use Bitrix\Main\Loader;
use Bitrix\Iblock\ElementTable;

Loader::includeModule('iblock');

$res = ElementTable::getList([
  'select' => ['ID', 'NAME'],
  'filter' => ['IBLOCK_ID' => 5, 'ACTIVE' => 'Y']
]);

while ($row = $res->fetch()) {
  echo $row['NAME'];
}
```

Здесь мы используем ORM: `ElementTable` — это класс, описывающий таблицу `b_iblock_element`. Мы не пишем SQL, структура описана в коде, и поля объявлены заранее.

#### Пример не-ORM подхода

```php
CModule::IncludeModule('iblock');

$arFilter = ["IBLOCK_ID" => 5, "ACTIVE" => "Y"];
$arSelect = ["ID", "NAME"];

$res = CIBlockElement::GetList([], $arFilter, false, false, $arSelect);
while($ob = $res->GetNext()) {
  echo $ob['NAME'];
}
```

Здесь используется устаревший API. Класс `CIBlockElement` — это просто обёртка, не знающая структуру таблицы. Все поля указываются вручную, типы не проверяются, связи не поддерживаются.

#### В чём разница:

* **ORM** знает структуру таблицы, поддерживает связи, позволяет расширять сущности.
* **Не-ORM** работает как чёрный ящик, всё через массивы и строковые ключи.

### Сущности
В контексте HL-блоков **сущность** – это та самая структура (класс), которая представляет ваш HL-блок. После компиляции HL-блока вы получаете ORM-сущность, через которую выполняются все запросы к данным блока. Это ключевое понятие ORM: думать в терминах объектов (сущностей), а не таблиц. Для новичка можно сказать так: сущность = «класс таблицы». Например, сущность HL-блока “`ProductCatalog`” позволит оперировать записями каталога как объектами класса `ProductCatalogTable`, а не как строками SQL.
**Highload-блоки** (иногда их называют HL-блоки) – это специальный модуль 1С-Битрикс для хранения больших объёмов данных в отдельной таблице базы данных. По сути, HL-блок представляет собой отдельный справочник (таблицу) с произвольными полями, который создан для быстрого доступа и работы под высокой нагрузкой. В отличие от стандартных инфоблоков, где элементы разных разделов часто хранятся вместе и их свойства распределяются по нескольким связанным таблицам, каждый HL-блок хранится в своей собственной таблице в базе данных и использует индивидуальные индексы. Это означает, что данные HL-блока изолированы от других, что уменьшает взаимное влияние разных сущностей друг на друга. Инфоблоки же – это основной модуль для контентных данных (новостей, товаров и т.д.), и у них богатый функционал (разделы, свойства, версии), но за это приходится платить производительностью и усложнённой структурой хранения.

### Различия HL-блоков и Инфоблоков

| Показатель                 |           HL-блоки           |                   Инфоблоки |
| -------------------------- | :--------------------------: | --------------------------: |
| Хранение данных            |     Собственные таблицы      |      Общая таблица для всех |
| Поддержка иерархии         |             Нет              |                        Есть |
| ORM                        |    Полная поддержка (D7)     |    Частичная, через обёртки |
| Производительность         |           Высокая            |     Ниже на больших объёмах |
| Количество свойств         | Ограничено возможностями БД  |              Неограниченное |
| Интерфейс администратора   |    Простой (ограниченный)    |  Развитый, встроенные формы |
| Связи между элементами     |        Только вручную        |            Есть типы связей |
| Поддержка мультиязычности  |             Нет              |                        Есть |
| Поддержка бизнес-процессов |             Нет              |                        Есть |
| Подходит для               | Справочников, больших таблиц |    Контент, каталоги и т.д. |
| Хранение файлов            |        Через UF-поля         |            Родная поддержка |
| API                        |          Через ORM           | Через CIBlockElement и т.д. |
| Генерация формы для ввода  |             Нет              |               Автоматически |



Highload-блоки - это быстрые справочники, без поддержки иерархии, с ограниченной поддержкой свойств. Они могут обращаться к БД в том числе и через HandlerSocket и работать с большими объёмами данных. Highload-блоки хранят элементы в своих таблицах и используют свои индексы.

### Начало работы

Разберём по шагам: чтобы начать работать с HL-блоком из PHP-кода, мы сначала загружаем информацию о нём из базы:
```php
$hlblock = Bitrix\Highloadblock\HighloadBlockTable::getById($HLBLOCK_ID)->fetch();
```
Эта строчка достаёт основные сведения о HL-блоке (его имя, таблицу и пр.) по ID. Затем:
```php
$entity = Bitrix\Highloadblock\HighloadBlockTable::compileEntity($hlblock);
```
Мы передаем эти сведения методу `compileEntity`, и он инициализирует класс сущности для данного highload-блока. Что значит "скомпилировать сущность"? Под капотом Bitrix берёт название HL-блока (`$hlblock['NAME']`) и на его основе формирует PHP-класс. Обычно класс называют как `<NAME>Table` – например, если `NAME` = ProductCatalog, класс будет `ProductCatalogTable`. Этот класс наследует от базового класса ORM (`Bitrix\Main\Entity\DataManager`) и автоматически получает всю необходимую структуру:
- Задает, с какой таблицей работать (берется из $hlblock['TABLE_NAME']).
- Добавляет поля, соответствующие пользовательским полям HL-блока (все UF_... поля из этого блока, а также стандартное поле ID)
- Подключает методы add, getList, update и т.д., унаследованные от DataManager, для работы с записями.

Фактически, compileEntity динамически генерирует PHP-класс. В памяти приложения появляется новый класс, с которым мы дальше можем работать. Метод возвращает объект Entity – по сути метаданные сущности – из которого можно получить название класса:
```php
$dataClass = $entity->getDataClass();
```
Теперь переменная `$dataClass` содержит строку с именем сгенерированного класса (например "`ProductCatalogTable`"), и через него мы уже выполняем запросы: `$dataClass::getList(...)` и т.д.

### Что делает `compileEntity`?

Метод `HighloadBlockTable::compileEntity($hlblock)` используется для генерации ORM-сущности во время выполнения.
Он необходим, потому что HL-блоки создаются динамически через админку и не имеют заранее описанного PHP-класса.

* Получает данные HL-блока (ID, NAME, TABLE_NAME)
* Формирует PHP-класс (например, `ProductCatalogTable`), наследующий `DataManager`
* Автоматически добавляет `getTableName()`, `getMap()` и стандартные ORM-методы (`add`, `getList`, `update`, `delete`)

После компиляции можно обращаться к ORM-классу через `$dataClass = $entity->getDataClass()`

### Пользовательские поля (UF_*)

Все поля в HL-блоках — это **user fields**, как в других модулях Битрикса. Их код всегда начинается с `UF_`.

**Добавление:**

* Через интерфейс админки: тип поля, обязательность, индексируемость и др.
* Или программно через `CUserTypeEntity`

**Хранение:**

* Обычные поля хранятся прямо в таблице HL-блока
* Множественные — в отдельной таблице `b_utm_hlblock<ID>`

**Чтение и запись:**

* Работают через ORM (`getList`, `add`, `update`)
* Все поля доступны по коду: `$row['UF_NAME']`, `$filter = ['UF_COLOR' => 'Red']`

**Особенности:**

* Для справочников важно поле `UF_XML_ID`
* Нет поддержки иерархии (разделов)
* Таблицы независимы, можно масштабировать

### Пример кода

```php
use Bitrix\Highloadblock as HL;
use Bitrix\Main\Entity;

\Bitrix\Main\Loader::includeModule('highloadblock');

$hlBlock = HL\HighloadBlockTable::getById(1)->fetch();
$entity = HL\HighloadBlockTable::compileEntity($hlBlock);
$dataClass = $entity->getDataClass();

// Добавление
$dataClass::add([
  'UF_NAME' => 'Иван',
  'UF_MESSAGE' => 'Привет!',
  'UF_DATETIME' => new \Bitrix\Main\Type\DateTime()
]);

// Получение
$result = $dataClass::getList([
  'select' => ['ID', 'UF_NAME', 'UF_MESSAGE', 'UF_DATETIME'],
  'order' => ['UF_DATETIME' => 'DESC'],
  'limit' => 50
]);
while ($row = $result->fetch()) {
  echo $row['UF_NAME'] . ': ' . $row['UF_MESSAGE'];
}
```

### Зачем нужен `compileEntity`

Без него нельзя работать с HL-блоком через ORM — система не знает, как обращаться к таблице. Метод создаёт ORM-сущнос


## Table Data Gateway в Highload-блоках

Ранее в системе использовался паттерн **Table Module** — для каждой таблицы создавался класс, содержащий в себе как работу с данными (SQL-запросы), так и бизнес-логику. Это приводило к сильной связке между структурой таблицы и логикой, усложняя поддержку и расширение кода.

С внедрением Highload-блоков в ядро D7, вместо Table Module используется **паттерн Table Data Gateway**. Теперь:

- Таблицей управляет отдельный слой — **Gateway**, отвечающий только за SQL-запросы (`find`, `insert`, `update` и др.);
- **Бизнес-логика** выносится в отдельный расширяющий класс, который разрабатывается пользователем при необходимости.

### Пример:

```php
// Gateway — только доступ к таблице
class PersonGateway {
    public static function find($id) { ... }
    public static function insert($fields) { ... }
}

// Отдельный класс с логикой
class PersonLogic extends HighloadBlock {
    public function getAdults() {
        $all = PersonGateway::findAll();
        // бизнес-логика фильтрации
    }
}
```

## Преимущества Highload-блоков
- Низкие накладные расходы (PHP, меньше запросов SQL).
- Низкий риск блокировок в БД: так как данные хранятся в своих таблицах, нет единой, глобальной таблицы, которая может заблокироваться при больших нагрузках (выборка и одновременно импорт).
- Тысячи, миллионы сущностей, справочники.
- Снижение нагрузки на БД, хостинг.
